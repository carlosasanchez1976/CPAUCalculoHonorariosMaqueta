SPEC: Responsive Design para Escalas de Windows
Fecha: 21/05/2026
Versión: 1.0
Estado: 📋 EN ANÁLISIS
================================================================================

CONTEXTO:
La aplicación fue diseñada en escala 100% (1920x1080). Al cambiar la escala de
Windows a 125% o 150%, se producen desbordes y desalineaciones visuales.

OBJETIVO:
Implementar márgenes adaptativos por escala de Windows que preserven el diseño
original en 100% y mantengan márgenes visibles en 125% y 150%.

ESTRATEGIA:
- Mantener variable --layout-padding-x: 150px como base (escala 100%)
- Usar @media (min-resolution: 1.25dppx) para escala 125%
- Usar @media (min-resolution: 1.5dppx) para escala 150%
- Mantener variables de fuente y spacing con clamp() (escalan suavemente)

SUBTAREA #003.4 ✅ - Eliminar max-width: 1400px del .cardsGrid
--------------------------------------------------------------------------------

  DESPUÉS:
    width: 100%;
    (eliminados los 3 anteriores)

CAMBIO en .cardsGrid @media (1025-1280px):
  ANTES:  max-width: 1200px;
  DESPUÉS: (eliminado)

RESULTADO: El grid llena el ancho completo de .content, alineado con el

✅ Escala 125%: 4 cards visibles sin solapamiento, badge dentro de cada card

LECCIONES APRENDIDAS:
- Un grid con minmax(0, 1fr) NO es suficiente si los items tienen min-width fijo
- Elementos con flex-shrink: 0 dentro de contenedores que se comprimen causan
  overflow, no shrinking
- Para badges/etiquetas en esquinas: position: absolute es más robusto que flex
- Un max-width interno + autocenter (margin: 0 auto) en una sección rompe la
  alineación con otras secciones del mismo contenedor que NO tienen ese
  max-width → evitar restricciones de ancho duplicadas dentro de la misma
  página (#003.4)
- Tamaños fijos en px (font-size, max-width, max-height) impiden la
  responsividad cuando los contenedores se comprimen → preferir variables
  con clamp() y dejar que los contenedores fluyan al ancho disponible (#003.5)
- Siempre validar visualmente en las 3 escalas; los cálculos teóricos no
  capturan problemas de elementos internos (badge, padding, etc.)

La aplicación usa márgenes laterales que se adaptan a la escala de Windows:

    padding: 0 150px;       /* Píxeles fijos */
    font-size: 24px;         /* No escala */
    gap: 24px;               /* No escala */
  }

### Cómo probar antes de hacer PR

1. Configurar Windows en escala 100% → verificar diseño
2. Cambiar a escala 125% → verificar sin overflow
3. Cambiar a escala 150% → verificar funcionalidad
4. Probar en mobile (DevTools, viewport 375px)

TICKET #009 ✅ COMPLETADO (22/05/2026)
================================================================================
TÍTULO: DashboardPage - Tipografía fluida en texto de bienvenida

PRIORIDAD: 🟡 MEDIA
TIEMPO ESTIMADO: 20 minutos
DEPENDENCIAS: Ninguna (refinamiento post-cierre del SPEC007)

CONTEXTO:
Al revisar el Dashboard en distintas escalas de Windows, se detectó que el
texto de bienvenida se ajustaba al contenido (wrap correcto), pero el tamaño
de la fuente NO escalaba proporcionalmente: se veía visiblemente más grande
respecto al viewport efectivo en escalas 125% y 150%, generando 3-4 líneas
por párrafo en lugar de las 2 líneas del diseño original (1920px @ 100%).

ORIGEN DE LA DISTORSIÓN:
.welcomeTitle usaba `font-size: 28pt` (≈37.3px), una unidad ABSOLUTA que no
escala con el viewport. Esto rompía la "regla de oro" #4 del README
(tipografía fluida con clamp()).

Matemática del problema (porcentaje del viewport ocupado por la fuente):
  Escala 100% (1920px): 37px / 1920 = 1.94%  ✅ Proporcionado (original)
  Escala 125% (1536px): 37px / 1536 = 2.41%  ⚠️ +24% relativo
  Escala 150% (1280px): 37px / 1280 = 2.91%  ❌ +50% relativo

Adicionalmente, los media queries existentes pisaban con valores fijos
(1.5rem en tablet, 1.375rem en mobile) en lugar de permitir una transición
fluida.

ARCHIVOS AFECTADOS:
- App/Frontend/src/pages/DashboardPage.module.css

CAMBIOS APLICADOS:

ANTES (incorrecto):
  .welcomeTitle {
    font-size: 28pt;   /* unidad absoluta, no escala */
  }
  @media (max-width: 1024px) {
    .welcomeTitle { font-size: 1.5rem; }   /* override fijo */
  }
  @media (max-width: 768px) {
    .welcomeTitle { font-size: 1.375rem; } /* override fijo */
  }

DESPUÉS (correcto):
  .welcomeTitle {
    font-size: clamp(1.375rem, 0.625rem + 1.4vw, 2.333rem);
    /* min 22px (mobile) → fluido → max 37.3px (≈28pt @ escala 100%) */
  }
  /* media queries ya no overridean font-size: el clamp() cubre todo el rango */

COMPORTAMIENTO ESPERADO:
  Viewport 1920px (escala 100%) → ~37px   ✅ idéntico al diseño original
  Viewport 1536px (escala 125%) → ~31.5px ✅ proporcional
  Viewport 1280px (escala 150%) → ~28px   ✅ proporcional
  Viewport 1024px (tablet)      → ~24px   ✅ legible
  Viewport <768px (mobile)      → 22px    ✅ mínimo del clamp

CRITERIO DE ACEPTACIÓN:
✅ Texto de bienvenida mantiene proporción visual al diseño original
   en escalas Windows 100%/125%/150%
✅ Se eliminaron los font-size fijos en media queries
✅ Comentario en CSS explica la decisión y el comportamiento esperado
✅ No genera overflow horizontal en ninguna escala

VALIDACIÓN VISUAL:
- Comparar contra el diseño cliente (3 párrafos × 2 líneas en full HD)
- Verificar en escala 100%, 125% y 150% de Windows
- Verificar en breakpoints tablet (1024px) y mobile (768px)

SUBTAREA #009.1 ❌ REVERTIDO (22/05/2026)
--------------------------------------------------------------------------------
TÍTULO: DashboardPage - Limitar ancho del contenido para emparejar márgenes
        con el diseño original del cliente

ESTADO FINAL: REVERTIDO — la propuesta era incorrecta.

CONTEXTO ORIGINAL:
Tras corregir el font-size del texto de bienvenida (Ticket #009), al comparar
contra la maqueta del cliente en resolución 1920x1080 @ escala 100% se
percibió un "espacio muerto" entre el texto de bienvenida y la card. Se
propuso limitar el ancho del contenido con max-width: 1200px + margin: 0 auto.

POR QUÉ SE REVIRTIÓ:
Al aplicar el cambio, se rompió una regla de diseño FUNDAMENTAL que ya
estaba resuelta en tickets anteriores del SPEC007:

  ⚠️ REGLA DE ORO: El contenido de cada página DEBE alinearse
     verticalmente con:
       - Borde izquierdo: logos del Header ("Calculadora DE HONORARIOS")
       - Borde derecho:   user-box del Header ("Usuario del Sistema")
       - Y replicar esa misma alineación en el Footer.

Esa alineación está garantizada por `--layout-padding-x` (150px/100px/70px
según escala Windows). Al introducir `max-width: 1200px; margin: 0 auto`
en .twoColumnLayout, el contenido quedó CENTRADO en el viewport en lugar
de respetar los bordes definidos por el padding lateral. Resultado:

  - Texto desalineado respecto al logo (margen izquierdo mayor que el header)
  - Card desalineada respecto al dropdown de usuario
  - Texto comprimido en columna más angosta → wrapping innecesario

El cliente envió maquetas con líneas verticales rojas que demarcan
explícitamente esos límites de alineación.

DIAGNÓSTICO CORREGIDO:
El "espacio muerto" percibido inicialmente era consecuencia del Ticket

PROBLEMA DETECTADO (validado empíricamente en máquina del usuario):
Todo el approach responsive de SPEC007 se basaba en detectar la escala de
Windows vía `@media (min-resolution: 1.25dppx)` y `1.5dppx`. Ejecutando
en consola del navegador:

  Escala Windows  | viewport     | window.devicePixelRatio | Regla activa
  ----------------|--------------|-------------------------|----------------
  100% wide       | ≥1600        | 1.0                     | 300px ✅
  125%            | 1188         | 1.0  ← NO es 1.25       | 150px ❌ (debía 100)
  150%            |  867         | 1.2  ← NO es 1.5        | 150px ❌ (debía 70)

CAUSA RAÍZ:
`window.devicePixelRatio` en Chrome/Windows NO refleja la escala del SO
de forma confiable. Depende de:
  - Configuración "Override high DPI scaling behavior" del .exe de Chrome
  - Drivers de gráficos / monitor
  - Versión del navegador
  - Settings del display
Esta inconsistencia es un problema conocido y `min-resolution` NO sirve
como breakpoint cross-environment.

Lo que SÍ es confiable: el **viewport width** (`window.innerWidth`) varía
consistentemente con la escala de Windows.

DECISIÓN DE DISEÑO:
Reemplazar TODOS los breakpoints basados en `dppx` por breakpoints basados
en `min-width`/`max-width` del viewport.
